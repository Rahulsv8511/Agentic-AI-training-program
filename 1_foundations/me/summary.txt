Product1 Explanation:
I built an AI-powered Data-as-a-Service platform for healthcare for transforming unstructured real-world data into high-quality structured data. By automating data curation with machine learning, it delivers results with exceptional speed and accuracy – empowering healthcare organizations to unlock insights faster.
In simple terms,The application's interface was split into two main sections: a PDF viewer on the left and a data entry panel on the right. On the left, for the selected PatientID, PDF and OCR are loaded and users scroll through large patient documents (with search functionality to find keywords) in the PDF display area. On the right, labeled fields are organized by category (e.g. Diagnosis, Pharmacy, Lab Report) for capturing structured data like cancer type, stage, drug names, dosages, test results, and dates. Each piece of information entered is linked to evidence in the PDF, and the interface includes a manual review feature: a second reviewer can see the captured data alongside the highlighted source snippet from the document, verify its accuracy, and then approve or correct it. This design enables fast, accurate conversion of unstructured medical records into high-quality structured data, while the built-in review mechanism ensures data integrity and compliance.


Product Vision (MVP): Empower healthcare teams with a fast, scalable, and secure data platform that effortlessly transforms massive patient document collections into accessible, high-quality information. This MVP lays the foundation for efficient oncology data management – delivering a user-friendly, high-performance solution that supports multiple cancer types, ensures HIPAA compliance, and enables collaborative review of curated data for accuracy.

Key Success Metrics for the MVP
To know if our MVP is succeeding, we’ll track a focused set of Key Performance Indicators (KPIs) aligned with the vision and critical features:
Load & Display Speed: Measures responsiveness. We want users to load large PDFs or image stacks without waiting. For example, aim for <2 seconds to open a 50-page document and near-instant page flips. This directly reflects the “high performance” goal for large document sets. We will test this with real patient files and measure average and 95th-percentile load times.
Concurrent Users: Ensures the system can handle multi-user demand. We’ll simulate dozens of users performing actions at once and track server response times and error rates. A key metric could be “max concurrent users with sub-second response times.” This validates the architecture’s scalability under load (e.g., multi-threading, load balancing working as intended).
Throughput (Documents/Hour): This composite metric gauges scalability to different data types and volume. It’s essentially how many documents can be ingested and displayed per hour when the system is at steady state. If we support more cancer types (each with varied document structures), the system should still handle volume. An increasing throughput over iterations indicates performance tuning success. This metric captures both system efficiency and how quickly a user can navigate/curate records (so it's influenced by UI usability too).
User Adoption & Engagement: Since we emphasize an easy UI for adaptability, we’ll monitor usage statistics. E.g., “What percentage of our pilot end-users shift to using this tool for their daily document work versus old methods?” A high adoption rate (say >90% after 1 month) means the MVP is intuitive and valuable. We can also track average session length or tasks completed per session to see if users are fully utilizing the system. Early user satisfaction surveys (qualitative metric) complement this, focusing on UI ease and workflow fit.
Data Accuracy (Review Discrepancy Rate): Our manual review mechanism is in place to ensure quality. We will measure the proportion of curated data fields that pass reviewer approval without changes. If reviewers consistently correct certain fields, that’s an issue to address (either training or tool output). For MVP, since much curation might still be manual, this is more about whether our interface prevents human errors and captures evidence properly. A goal might be >95% of fields require no correction upon review (meaning the combination of user+tool works well). We’ll also track review time per record as a sub-metric (to ensure the review process is efficient, not bogging down).
Compliance Checks: While “100% compliance” is not a typical numerical KPI, we will treat regulatory requirements as must-hit targets. We’ll verify that all data access is logged, encryption is always on, and no PII leaks. We might create an internal compliance scorecard (covering HIPAA requirements) and ensure MVP meets all points (e.g., access control implemented, timeouts and audit logs working)1. Success here is binary: either we meet compliance or we don’t. We’ll conduct a HIPAA compliance audit as part of MVP acceptance criteria. An associated metric might be “0 security incidents” or “Passed 100% of security test cases.”

What we built as part of MVP and why?
Bulk Document Loading & Display: Enabled users to open and navigate very large patient document sets. Rationale: This addressed the core need to view extensive medical records efficiently – a foundation for all other functionality.
High-Performance Multi-User Support: Built the system to handle many concurrent users without lag. Rationale: In a busy hospital setting multiple clinicians use the tool simultaneously, so ensuring fast response times under load was critical for user adoption and trust.
Scalability for Various Cancer Types/Data: Designed a flexible data model to accommodate different cancer categories and document formats from the start. Rationale: This ensured the MVP wasn’t a one-off solution – it could easily extend to new data sources and use cases, proving the platform’s robustness and future scalability.
Intuitive, Easy-to-Use UI: Delivered a clean interface with simple navigation and clear fields for data entry. Rationale: By minimizing training and simplifying workflows, we drove user adaptability – essential for getting early feedback and achieving widespread use of the MVP in a clinical environment.
Built-in HIPAA Compliance & Security: Implemented encryption, access controls, and audit logs as part of the MVP. Rationale: Handling patient data mandates privacy and regulatory compliance from day one; baking security in early avoided costly rework later and instilled confidence in the product among stakeholders (IT and clinical users alike).
Manual Review & Evidence Capture: Included a reviewer workflow where a second user can verify extracted data against highlighted source text in the documents. Rationale: This ensured high data quality and accuracy in the MVP phase, allowing mistakes to be caught and corrected. It also provided a feedback loop for improving the system (and training future AI models) while building user trust in the curated data.

Technical Product Manager’s Role and Responsibilities
Given the technical nature of this project (AI/NLP, cloud infrastructure, etc.), it’s crucial to have a Technical Product Manager (PM) who not only grasps product strategy but also understands the jargon and constraints of the technology. This person (essentially my role in this scenario) serves as the bridge between the engineering teams (front-end, back-end, NLP, QA) and the business/stakeholders. Here are the key responsibilities and areas of focus for the technical PM:
Defining Product Vision & Requirements: The technical PM translates the high-level vision (“faster, more accurate curation”) into concrete product requirements and features. They need to have a clear vision of how AI capabilities will solve user pain points6. This involves creating detailed product requirement documents (PRDs) that might specify, for example, “The system shall extract and populate field X with 85% accuracy by using NLP model Y.” They ensure that the requirements reflect both user needs (e.g., easy UI, evidence links) and technical feasibility (given current AI capabilities). Essentially, they own the what and why of the product, making sure the inclusion of AI features directly addresses user problems and business goals6.
Stakeholder Management and Communication: A technical PM must communicate effectively with a broad range of stakeholders – from hospital management and compliance officers to software developers and data scientists6. For each audience, they tailor the message: to execs, focus on business value and ROI; to engineers, clarify the user stories and acceptance criteria; to compliance/legal, detail how the solution meets regulatory requirements. They also align everyone on project progress and priorities, preventing disconnects. For instance, if data scientists hit a snag with model accuracy, the PM communicates implications to timeline with the business stakeholders. Conversely, if a stakeholder requests a change (“can we also capture this new field?”), the PM evaluates the impact and communicates with engineering. Aligning the cross-functional team is one of their core responsibilities5, making sure that clinicians’ needs, technical constraints, and business objectives all meet in the middle.
Technical Fluency & Jargon Translation: While they might not write the code, a technical PM in this AI project needs to be conversant in terms like OCR, NER, F1-score, AWS Textract, etc. When data scientists talk about model precision or an engineer talks about S3 bucket policies, the PM should understand and ask the right questions. They act as a translator between technical and non-technical realms6. For example, explaining to a non-tech exec why the model needs more training data or what it means that “precision is 95% but recall is 70%” in terms of business impact. This understanding also enables them to challenge or validate estimates – e.g., if an engineer says “integrating Textract will take 2 sprints,” the PM can gauge if that’s reasonable or if perhaps there’s an AWS service to expedite it. Technical acumen lends credibility and facilitates smoother planning because the team doesn’t have to dumb things down, and the PM can proactively identify technical dependencies or risks.
Backlog and Project Management: The technical PM owns the product backlog, writing user stories and epics that capture both user-facing features and technical work. They prioritize these in collaboration with the team, balancing feature development with technical debt and research spikes. For instance, an epic like “Develop NLP model for genomic data extraction” might need several research spikes or data collection tasks first – the PM will include those tasks and allocate time for them. They oversee the project timeline, setting milestones (MVP ready, Pilot test, Launch) and ensure deliverables stay on track66. If any task is at risk, they facilitate a solution (maybe de-scope something or add resources). They run sprint planning, stand-ups, and retrospectives in an agile environment, always tying the technical work back to the product goals.
Data Strategy & AI Model Oversight: In an AI product, the PM also plays a role in data strategy – making sure the team has the data needed and that it’s used responsibly5. For example, they might coordinate with IT to get access to historical records, or decide on using synthetic data to supplement. They also ensure the dataset covers the variety needed (so that the model isn’t biased). While the data scientists handle model training, the PM needs to understand the model’s evaluation results and decide if it’s fit for release. They set acceptance criteria like “model achieves at least 80% accuracy on key fields in validation”. They also plan how the model will be monitored in production and updated. Essentially, they guide model development by aligning it with the product needs – ensuring the AI isn’t just cool but actually solves the problem. If multiple approaches (say rule-based vs ML) are possible for a sub-problem, the PM weighs trade-offs with the team and stakeholders before committing.
User Experience & Workflow Design: The technical PM works with UX designers (if any, or directly with front-end developers) to craft how the user will interact with the AI features. This is a technical product, but usability is key to adoption. The PM specifies things like: how suggestions are displayed (e.g., highlighted field with confidence score?), how evidence is accessed, what happens on edge cases (no AI suggestion available, or AI is not confident). They gather input from users (curators) to ensure the workflow is intuitive. For example, if a curator says, “I need to see at least a snippet of the source, not just a link,” the PM translates that into a UI requirement. They focus on integrating the AI into the user’s natural workflow so it feels like a helpful assistant, not a hindrance5. They might produce wireframes or prototypes of the form with AI suggestions and iterate with user feedback. Post-launch, they continue to monitor UX: if users are skipping the AI suggestions or find the evidence viewing clunky, the PM will adjust requirements in future iterations.
Regulatory and Ethical Oversight: Especially in healthcare AI, the PM keeps a close eye on compliance. They ensure that any necessary documentation (like a privacy impact assessment, or if we were to ever seek an FDA clearance in future, the groundwork of data and testing is recorded) is in place5. Ethically, they also champion fairness and patient safety: e.g., making sure the AI’s errors can’t directly harm a patient record, establishing procedures for human review of low-confidence items (so that a marginal AI guess never goes unvetted). The PM might define a policy that “any field below 70% confidence will not be auto-filled – instead flagged for manual entry,” as a product rule balancing risk. They work with legal or compliance teams to incorporate any guidelines (for instance, if the hospital requires a disclaimer for AI-generated data, the PM adds that to requirements).
Monitoring and Iteration Post-Launch: Once deployed, the technical PM doesn’t step back; they monitor performance indicators and user feedback, and organize continuous improvements5. For example, if a certain field’s accuracy is consistently below target, they’ll prioritize a story to refine that (maybe retrain the model or adjust the extraction logic). If users request a new feature (like exporting the data to a spreadsheet), the PM evaluates and potentially adds to the roadmap. They also keep an eye on system health in production, ensuring any major issue (downtime, data issue) is addressed. Essentially, they lead the product lifecycle from conception through launch and beyond, making sure the product evolves to meet needs and stays successful66.
Cross-Team Coordination: In this particular project, we have distinct teams (Front-end, Back-end, NLP/AI, QA). The technical PM ensures these teams work in sync. For example, when the NLP team builds the model, the back-end must know how to call it and the front-end how to display results; the PM will schedule joint discussions or API agreements. They also help resolve priorities if one team is waiting on another. If the NLP model isn’t ready, the PM might have the front-end team work on other features rather than idle. They also align testing – making sure QA knows the intended behavior of AI features to write the right tests.
In summary, the technical product manager’s responsibilities can be seen as wearing multiple hats – strategist, communicator, technical liaison, and project manager all at once66. They ensure that the highly technical aspects (like model performance or AWS infrastructure choices) always serve the product’s objectives and user needs. They don’t necessarily code the solution, but they absolutely understand how it’s built and deployed. This understanding allows them to make informed decisions and keep the entire cross-functional team aligned toward the common goal: a successful, user-friendly, compliant AI product that delivers on its promises.
Product Roadmap (Phases & Timeline)
Building this AI-assisted medical data entry product is a significant undertaking, and a well-structured roadmap is essential to deliver it successfully. We will approach the development in phased milestones, allowing for iterative improvement, risk mitigation, and feedback incorporation at each stage. The roadmap will align the efforts of the front-end, back-end, NLP, and QA teams and ensure stakeholder visibility into progress.
Below is a high-level timeline with key phases of the product roadmap:
Let’s detail what each phase entails and how different teams contribute:
Phase 1: Discovery & Prototype (Q3 2025). This is the exploratory stage:
Activities: We will engage in deep requirements gathering – interview data curators, oncologists, and other stakeholders to refine which fields are most critical and pain points in the current process. We’ll also audit the available patient documents and manual data to understand data variety. Concurrently, a technical spike will be done: using a small sample of documents, we’ll run AWS Textract and Comprehend Medical to see preliminary results. For example, pick 10 patient files and see if Comprehend can identify key items (diagnosis, meds). We may also train a quick and dirty baseline model (perhaps using an existing open-source clinical BERT) just to test the concept of custom extraction for one field (like cancer stage).
Outcome: The result should be a proof-of-concept demo for internal stakeholders – e.g., a simple script that given a document prints out “I think Diagnosis = X, Stage = Y”. This helps sell the idea and also flush out obvious challenges early (maybe Textract struggled with scanned handwriting – we note that).
Deliverables: Product Requirements Document (PRD), initial UX wireframes for the form interface, a defined list of fields to tackle first (maybe a priority list), and success metrics defined (we confirm the >80% accuracy target, etc.). Also, a data strategy document – where will training data come from, how to label it – will be drafted.
Team Involvement: Minimal front-end now (perhaps just a mockup of UI), Back-end in setting up AWS access and trying out Textract/Comprehend, NLP team exploring model options and data requirements, QA not yet heavy (maybe they help verify outputs qualitatively). Also, IT/Security gives early guidance on compliance (e.g., spin up a secure AWS dev environment).
Phase 2: MVP Development (Q4 2025). This is heads-down building the minimum viable product that actually works end-to-end for a simplified scope:
Scope: We’ll target perhaps ~20 of the 150 fields – focusing on those easiest to extract (low-hanging fruit) and/or most valuable (high priority for curators). For example, fields like patient demographics (Name, DOB, etc.), primary diagnosis, a couple of key lab results, and maybe one genomic marker as a stretch.
Front-end Team: Develop the core UI components: the patient record page with the split view (documents on one side, form on the other). Implement form fields that can show AI suggestions – e.g., design a way to highlight them (maybe a blue outline indicating “AI-filled”) and an icon to view evidence. Also build the document viewer capability (which might be embedding a PDF viewer or image viewer) with ability to jump to a page and highlight text. The emphasis is on functionality over polish at this MVP stage.
Back-end Team: Set up the data pipeline on AWS. This likely involves writing Lambda functions or a backend service to orchestrate Textract and Comprehend calls. Also, design a simple database or storage for the results (even if just storing in memory or a JSON file for now). The back-end should expose an API that the front-end can call, like GET /autofill?patientId=123 returning JSON of field: value + evidence pointer. Basic authentication/authorization should be in place if needed (ensuring only authorized users can access certain patient data).
NLP Team: Work on the custom model for one or two fields that Comprehend doesn’t handle well (maybe the genomic data). At MVP, this could be a very rough model or even a rule-based approach, because training a full model might take longer. For instance, they might implement a regex or simple algorithm to find “Stage III/IV” in text as a placeholder solution, or use Comprehend output and apply some logic. The goal is to have something working even if not highly accurate yet, to prove the integration.
QA Team: Although development is ongoing, QA can start writing test cases. They will test things like: does the system properly fetch the documents? Does an AI suggestion show up when expected? What if the AI finds no info – is the field left blank gracefully? They’ll also test basic security (e.g., ensure data doesn’t leak in logs). Given this is healthcare, QA might do a preliminary HIPAA compliance checklist now: e.g., all web endpoints are HTTPS, no sensitive info stored in browser storage, etc.
Iteration: We’ll likely run this in sprints, delivering incremental pieces (first get Textract working for one doc, then add Comprehend, then hook to UI). By end of Q4, we aim to have a functioning MVP that a user can try on a small set of cases, even if accuracy is not great.
Stakeholder Checkpoint: At the end of MVP dev, we will demonstrate the working system to stakeholders (perhaps a live demo on a test patient). This manages expectations and generates excitement. We’ll clarify that this is an early version just for testing, not final accuracy.
Phase 3: Pilot & Model Refinement (Q1 2026). Now that the MVP is ready, we enter a pilot testing and iteration phase:
Pilot Deployment: We will select a small group of, say, 5-10 medical data curators (perhaps one from each team or site) to use the MVP on real patient records (or recently completed ones for comparison). This will likely be in a safe environment (e.g., double-checking all outputs before anything is finalized). The pilot might run for a few weeks, during which these users use the tool for their daily work (or in parallel to their manual work to compare results).
Feedback Collection: We’ll gather both qualitative and quantitative feedback. Qualitatively, through interviews or a feedback form: “Which features did you like? What was confusing? Did the AI miss common fields? Did it ever give wrong info that concerned you?” Quantitatively, from the pilot usage we’ll extract metrics: actual accuracy (how many suggestions accepted), time taken, etc., as described in metrics section.
Model Refinement: The NLP team will use pilot data to retrain or fine-tune models. For example, if we find the model struggled with a certain terminology, they’ll add those examples to training. Or they may incorporate additional data that became available. Also, if during MVP we had placeholder logic for some fields, now is the time to replace those with more robust ML models. We may expand to more fields now (maybe going from 20 fields to 100 fields coverage) by training models or configuring Comprehend properly for them.
Feature Enhancements: The front-end may be refined based on user feedback – maybe users wanted a clearer indication of AI confidence, so we could add a percentage or color code to suggestions. Or perhaps navigation between documents needed improvement, so we tweak that. The back-end might need optimization if pilot showed slowness (e.g., do Textract in parallel, or cache results for reuse). We also implement the human-in-the-loop feedback capture formally – ensuring that when users correct something, it gets logged for learning (if that wasn’t in MVP, we add it now).
Security Hardening: Before broader launch, we double-check security aspects: penetration testing or code review for vulnerabilities (especially since handling PHI), ensure audit logging is in place, etc. Given pilot involves real PHI, all security should already have been in place, but we do a thorough review here. Robust security measures must cover patient information2, so we involve the security team to audit the system.
Documentation & Training Prep: We prepare user guides, training materials, or even tooltips in the UI explaining how to use the AI features. Plan training sessions for the wider rollout. Also document processes for ops (e.g., how to recover if an AWS component fails, etc.).
Go/No-Go Decision: At end of Q1 2026, with pilot results in hand, we assess if the product meets the criteria for launch. Criteria could be: at least 80% accuracy on key fields in pilot, pilot user satisfaction above a threshold, no critical security or stability issues remain, and all necessary features for basic use are done. If not, we might extend pilot phase to improve those areas; if yes, we green-light moving to full deployment.
Phase 4: Full Launch (Q2 2026). This is when we release the product to all users and make it the primary way to do data curation:
Deployment: Roll out perhaps in waves – maybe one department or location at a time, or straight to all 3000 curators depending on confidence. We’ll coordinate with the IT department to deploy any necessary client updates or ensure everyone has access.
User Training & Change Management: Conduct training sessions (via webinars or in-person) for curators to learn the new system. Emphasize how to use evidence links, how to override AI entries, and reinforce that they remain responsible for final verification (to assuage any concerns). Provide support channels (helpdesk or chat group) for questions as they start using it daily.
Monitoring: In the launch period, closely monitor the system. The PM and team should set up a “war room” or at least a daily check-in on key metrics: Is the system latency OK? Any spike in errors or user complaints? Are suggestions being generated as expected? We likely integrate logging and monitoring tools (CloudWatch, etc.) to catch any performance issues. Also monitor adoption: ensure users are actually using it and not reverting to old ways. If some aren’t, reach out to understand why (maybe they need another training or had a bad first experience we can address).
All Fields Coverage: By launch, we aim to support all 150+ fields with at least some strategy (model or rule). However, transparency is key: if some low-accuracy fields are still “experimental,” we might label them as such or have them off by default. But ideally, we’d cover major ones confidently and perhaps leave a few rarely filled fields for manual entry as acceptable.
Performance Scaling: Ensure the pipeline can handle the full load (which could be spikes of dozens of simultaneous users processing large docs). By now, we’d have scaled up AWS resources appropriately (maybe using AWS’s auto-scaling for the model endpoint, etc.). The back-end team will ensure limits are set correctly (e.g., Textract job throughput).
Celebration: It’s worth noting a full launch is a major milestone – a brief celebration or acknowledgment of team effort keeps morale up. Then we quickly turn to support and maintenance mode in the immediate post-launch.
Phase 5: Expansion & Optimization (Second half 2026 and beyond). After initial launch, the work isn’t done. We move into a continuous improvement mode:
Accuracy Optimization: Analyze the data coming in from real usage. Perhaps we identify that out of 150 fields, 20 fields have accuracy < 70%. We create a focused plan to improve those (maybe new model training specifically for them, or adjust how we parse certain docs). We might also expand the training dataset now with thousands of real examples collected from launch usage (with user-validated answers). Aiming to push overall accuracy closer to 90% (industry benchmarks for mature systems are ~85-90%1).
New Document Types: Initially we might have focused on certain document sets (e.g. hospital reports). Later, we incorporate other sources like maybe pathology lab system outputs, or external physician notes which could have different formats. That might necessitate new parsing logic or model tweaks.
Additional Features: Based on user feedback and backlog priorities, we could add features. Some ideas: a dashboard for managers to see how many records were processed by AI, or a feature for curators to manually trigger re-running AI after they upload a new document. Maybe integration to automatically flag if certain critical fields are missing (kind of QA on the data).
Integration with Downstream Systems: If not already, we might integrate the output with other systems. For example, automatically update the central database or send data to an analytics platform for research. Stakeholders might ask, “Now that forms are digital, can we get analytics on how many Stage IV patients we had in last quarter?” – we could plan a reporting feature.
Scaling to More Users or Clients: If this tool could be used in other departments (maybe similar concept for cardiology forms, etc.), explore replication. Or if external clients (other hospitals) are interested, consider multi-tenancy. These would be future roadmap considerations once our initial use-case is rock solid.
Maintenance: Establish routine model retraining schedule (e.g., retrain every 6 months with latest data), and maintenance of AWS infrastructure (apply updates, manage costs). Also, keep an eye on AWS new features – perhaps AWS releases a new Comprehend Medical model with better capabilities, we’d want to incorporate that (so staying updated is part of PM’s job in long term).
KPIs and Monitoring Ongoing: Continue to track the metrics mentioned (accuracy, time saved, etc.). Perhaps set new targets as we improve (e.g., try to get adoption to 95%, or reduce manual correction rate to <5%). Regularly report these to stakeholders to show value (especially ROI or efficiency gains).
Feedback Loop: Create an easy way for users to provide feedback continuously (could be an in-app feedback button or quarterly surveys). This way, we keep a pulse on user satisfaction and catch issues or ideas for enhancements.
Each phase in the roadmap has distinct objectives and deliverables, and they build upon each other. Importantly, we’ve structured this roadmap to de-risk the project by doing a pilot before full launch (validating in a controlled way), and to incorporate user feedback early (so we don’t develop in a vacuum). We also aligned it roughly by quarters to set expectations with management about how long this will take – it’s a multi-quarter effort, which is realistic given the complexity.
Throughout these phases, maintaining agility is important. We will likely adjust the roadmap dates or scope as we learn more (especially from the pilot). But this phased approach ensures that by the time we launch widely, we have a well-tested, user-approved solution. Also, by Phase 5, the product will mature further, solidifying its value and keeping it ahead (continuously improving accuracy and features ensures it remains a worthwhile tool rather than stagnating).
Features, Epics, and User Stories (by Team)
To execute on the roadmap, we break down the work into epics (large feature areas) and user stories (specific functionality) that different teams will tackle. We have four primary development streams: Front-End, Back-End, NLP (AI Model), and QA (Quality Assurance). Below is a breakdown of major epics and example stories for each team:
Front-End Team
Epic 1: AI-Assisted Form Interface – Develop the user interface for curators to interact with AI suggestions on the form.
User Story: “As a data curator, when I open a patient’s record, I see the form fields pre-filled with suggested values from AI, so that I can review and confirm them.” – Acceptance Criteria: Fields are populated with a distinct style (e.g., italic text or colored background) to indicate AI input, and empty if no suggestion.
User Story: “As a data curator, I want to easily identify which fields the AI was confident about and which need my attention, so I know where to focus my review.” – Acceptance Criteria: Perhaps include a confidence indicator or flag low-confidence fields with a warning icon.
User Story: “As a data curator, I can edit or override any field the AI filled, so that I remain in control of the final data.” – Acceptance Criteria: Typing in a field with AI suggestion replaces the AI value, and the change is saved for that session.
Epic 2: Document Viewer & Evidence Linking – Integrate document display and highlight evidence snippets.
User Story: “As a data curator, I want to view the original document page that supports a suggested field value, so I can verify the information in context.” – Acceptance Criteria: Clicking an “evidence” icon next to a field opens the document viewer to the correct page and highlights the relevant text snippet.
User Story: “As a data curator, I can navigate through all patient documents within the app, so I don’t need external PDF viewers.” – Acceptance Criteria: The right-side viewer allows scrolling pages, switching documents, zooming, etc., to inspect all content if needed.
User Story (Stretch): “As a data curator, I can see a summary list of what data was pulled from each document,” – so perhaps a sidebar list like “Document A provided 5 fields: [list]”. This can help users trust and cross-check.
Epic 3: User Feedback and Controls – Features that let users provide input back to the system.
User Story: “As a data curator, I want to mark an AI suggestion as incorrect easily, so that the system can learn from mistakes and I can signal it was reviewed.” – Acceptance Criteria: A simple “thumbs down” or checkbox that the user can tick if an AI field was wrong, logging that feedback.
User Story: “As a data curator, I want to trigger the AI to re-run on a document after I add or correct something,” – e.g., if a user uploads an additional document or adjusts part of text, they might want to re-fetch suggestions. (This might be an advanced case, possibly handled via page refresh in MVP but refined later.)
Epic 4: UI Usability & Accessibility – Ensure the interface is user-friendly and accessible.
User Story: “As a visually impaired user (or simply per accessibility standards), I can use keyboard shortcuts or screen-reader to go through suggestions,” – ensure compliance with UI accessibility guidelines.
User Story: “As a user, I want a short tutorial or tooltip hints on first use of the AI-assisted form,” – to get up to speed quickly. (Maybe an overlay highlighting “this is an AI-suggested field, click here to see evidence, etc.”)
Each user story will be refined with the front-end team and UX designer to ensure the design meets the needs. Many of these focus on making the AI assistance transparent and easy to control, addressing the trust aspect by design.
Back-End Team
Epic 1: Document Ingestion Pipeline – Handling retrieval and text extraction from documents.
User Story: “As the system, when a user opens a patient record, I must fetch all relevant documents from S3 and extract text from them,” – Acceptance Criteria: For a given patient ID, the text content of each document is obtained (via Textract or direct text extraction), ready for NLP processing.
User Story: “As the system, I process documents in parallel to minimize wait time,” – ensure our pipeline can handle multiple pages/docs concurrently to speed up response.
User Story: “As the system, I securely cache extraction results for documents that have been processed, so that reopening the same patient doesn’t redo work unnecessarily,” – useful if a user revisits record or multiple users access the same patient.
User Story (Error case): “As the system, if a document is unreadable or the text extraction fails, I flag it and still proceed with other documents,” – to handle partial failures gracefully (and maybe inform the user “Document X couldn’t be processed”).
Epic 2: NLP Processing & AI Integration – Coordinating with AWS Comprehend Medical and custom models.

Hypothetical Stakeholder Conflicts and Resolutions
Building an innovative AI solution in a healthcare setting will likely surface conflicts or concerns among stakeholders. A product manager must navigate these diplomatically, finding resolutions that maintain project momentum while addressing valid points. Here are some hypothetical conflict scenarios and how we’d handle them:
Conflict 1: Data Security Concerns vs. Cloud Deployment
Stakeholder POV: The hospital’s Chief Security Officer (CSO) or Compliance Officer is uneasy about uploading sensitive PHI to the cloud (AWS). They question whether this violates HIPAA or introduces breach risks: “How can we trust that patient data in AWS will remain private? What if AWS staff access it? Are we exposing ourselves to hacks?”
PM Resolution: First, acknowledge the importance of their concern – we too prioritize patient privacy. Then, provide concrete assurance: explain that AWS is a HIPAA-compliant environment under our BAA2. Detail the security measures in place: all data is encrypted in transit and at rest with robust encryption keys, strict IAM roles prevent unauthorized access, and we’ll employ VPC isolation so data doesn’t traverse public internet2. Perhaps share documentation of AWS’s compliance and even involve an AWS solutions architect to talk to security stakeholders.
Emphasize that automated AWS services actually reduce the chance of human error (no physical tapes or local servers to misplace). Also propose a penetration test or security audit that the security team can conduct on the solution before full rollout, to gain confidence.
Finally, highlight that this solution replaces a very manual process that might have its own security issues (e.g., paper records or local spreadsheets that are less secure). Show that by centralizing in AWS with proper controls, security is actually enhanced, not weakened.
Outcome: The CSO is satisfied after reviewing the security architecture and possibly after we agree to additional monitoring (e.g., CloudTrail logs will be shared with the security team for oversight). We turn a potential blocker into an ally by involving them in the design of security features.
Conflict 2: User Resistance – Curators Fear Job Displacement or Extra Burden
Stakeholder POV: Some medical data curators are skeptical or worried about the new tool. Comments might include: “Is this AI going to make my role redundant?” or “I’ve been doing this manually for 10 years, I trust my way more than some algorithm” or even “This sounds like extra work to learn – will it slow me down initially?” There could be a passive resistance to adoption if they feel it’s imposed.
PM Resolution: This is largely a change management and communication challenge. We’d address it by clearly communicating the purpose and benefits of the AI tool: it’s there to assist and speed up their work, not to eliminate the need for them. In fact, we can reassure them that their expertise is still critical – the AI is not making decisions, it’s just retrieving data for them to verify3. Use analogies (like how spell-check assists writers – it doesn’t replace them but catches typos).
We also involve them early: perhaps some of these skeptics were in our pilot program so they saw it in action and gave input. If not, we can have a demo session where one of their peers (pilot user) shares their positive experience (“I was able to get through my cases in half the time”). Hearing from a fellow curator might alleviate fears more than hearing from a PM.
Training and gradual introduction are key: we could start with voluntary use – “Try it for some records and see how it helps” – rather than forcing it overnight. Once they see time saved, they’ll be more convinced. And definitely address the skill aspect: ensure the UI is user-friendly and provide hands-on training. Perhaps assign a super-user or help-desk person to rapidly answer any questions in the first weeks.
Also, explicitly state that no job losses are planned due to this tool; rather, the organization plans to reallocate freed time to other important tasks (or handle more patients with the same team).
Outcome: Over time, curators begin to see the AI as a helpful colleague rather than a threat. Early critics might become neutral or even advocates once they realize it reduces drudgery (no one enjoys flipping through hundreds of pages for a lab value). The PM continuously gathers feedback and ensures their concerns (like if the AI made a dumb error) are heard and fixed, further building trust. This conflict dissipates with transparency, training, and evidence that the tool truly helps them.
Conflict 3: Model Accuracy vs. Launch Timeline (Quality vs. Speed to Market)
Stakeholder POV: Senior leadership (e.g., COO or Project Sponsor) is eager to realize the efficiency gains and might push for launching ASAP, perhaps to meet a fiscal year goal or because they announced it in an initiative. Suppose our pilot showed 75% accuracy, which is below the 80% target, but the COO says, “This is good enough, let’s roll it out now and improve later. We can’t afford to wait another quarter.” On the other side, the Data Science lead might be saying, “If we launch with 75%, users will see too many errors and lose faith; we need a bit more time to get to our benchmark.” This creates a tension between a business push for speed and a technical caution for quality.
PM Resolution: This needs a balanced approach. First, analyze the impact of 75% accuracy – which fields are failing, and are they critical? If the errors are in relatively minor fields or things that users can easily fix, maybe it’s not so bad. But if core fields like diagnosis have issues, that could indeed erode trust.
I would present to the COO a data-driven argument: e.g., “During pilot, out of 100 fields, 25 had to be corrected. Users expressed frustration particularly when the AI got X wrong. If we launch widely now, we risk a poor first impression and people might revert to manual work, undermining the ROI. However, if we take 4 more weeks, our data scientists estimate we can reach ~85% by adding these new training data and tweaks, which would make the user experience significantly smoother.”
Also propose a compromise: a phased launch – for instance, launch in read-only assist mode (AI suggests but doesn’t auto-fill) or launch only to a subset of users who are enthusiastic, while the team continues improving the model in parallel. This way, we meet the desire to start rolling it out, but we limit exposure of potential quality issues. The phased approach can be framed as part of the plan (not a delay) – “We do a soft launch to early adopters in Q2, incorporate their feedback, and a full launch in Q3 with improved accuracy.”
Emphasize long-term success: It’s more costly to lose user trust and have to win it back than to launch a bit later with a solid product. Also, tie to metrics leadership cares about: if adoption suffers due to low accuracy, the efficiency gains (and thus ROI) won’t materialize. Better to ensure a positive reception.
Outcome: The COO agrees to a short extension or the phased approach. We clearly communicate the adjusted plan to all stakeholders so it doesn’t appear as a failure but as a strategy for success. The data science team gets the needed time, and we maybe even involve the COO in periodic check-ins to see the accuracy improving, keeping confidence high. Ultimately, we launch with a quality level that sustains user trust, which aligns with the business’s ultimate interest in adoption and ROI.
Conflict 4: Scope Creep – Additional Stakeholder Demands
Stakeholder POV: Perhaps the IT Director says, “Since we’re doing this, can we also implement it for our cardiology department’s forms? And can we integrate it with the EHR so doctors can use it too? Oh, and maybe include a chatbot for querying records.” They see many possibilities and want them all at once. Another example: A compliance officer might suddenly say, “We need an exhaustive audit report feature from day 1 for every field change for compliance” which wasn’t originally in scope in detail.
PM Resolution: These requests, while potentially valuable, can jeopardize the project by diluting focus or extending timelines. The PM should handle this by referring to the product vision and current scope commitments. A polite but firm response: “Those are excellent ideas and definitely on our radar. Right now, our priority is to nail the oncology use-case because that’s where the immediate pain point and ROI are. We have built the foundation in a way that could support cardiology later, but doing it now would push our timeline by X and introduce additional risk. How about we schedule that as phase 2 after we launch this successfully?”
The key is to acknowledge the idea (maybe put it in the roadmap backlog) but defer it by highlighting the importance of getting one use-case right first. Also, sometimes quantifying the impact helps: “Adding cardiology would double our document types to handle – likely requiring another 3 months and more data training. It might be better to get oncology live (saving us Y hours per month) and then use that momentum to expand.”
For compliance features, if truly needed, determine if it's a “must-have” or “nice-to-have”. If must-have (like audit logs), ensure it’s in scope (perhaps it already is). If it’s an extra like “exhaustive report generation,” maybe say we’ll do a simpler version now (logs accessible in raw form) and a pretty report UI later.
Outcome: Stakeholders usually understand trade-offs when explained in terms of time and outcomes. By documenting these requests and scheduling them for later, they feel heard. The roadmap might get an added Phase 6 in 2027: “Expand to other departments” which satisfies them that it’s considered. Meanwhile, the team remains focused on core deliverables. This avoids the project ballooning beyond control and failing to deliver the primary value.
Conflict 5: Clinician Trust – Doctors Question AI Accuracy
Stakeholder POV: Even though doctors aren’t the direct users, they rely on the data curators enter. A senior clinician might say, “If this AI pulls data, how do we ensure it doesn’t miss something important? I’m worried about relying on AI-curated data for patient decisions. We’ve seen cases where AI algorithms had bias or errors – who is accountable if something is wrong in the record?” They might be wary of any AI involvement in patient data.
PM Resolution: This is about ensuring clinical trust and accountability. Response: The final responsibility remains with the human curator – they verify every piece of data. The AI is a tool, like a high-powered magnifying glass, not an independent decision-maker. To alleviate concerns, mention that we have the evidentiary trace for every datum (so if a doctor doubts a piece of data, the source document is just a click away).
Also, explain the thorough validation we’ve done: real-world testing, high accuracy on retrospective data. If possible, share some results with the clinicians: e.g., “We ran this on 100 past cases and it captured 98% of key findings – and in 2% of cases it missed something, the curator caught it. It never introduces totally fake info because we tie everything to source text.”
Moreover, propose involving a clinician in reviewing the output periodically – an oversight process to ensure it’s clinically sound. This might be in the form of a medical informatics specialist doing spot checks on samples of AI-curated records. Knowing there’s governance can reassure them.
In terms of accountability, clarify that the workflow and training reinforce that curators must confirm all data, so it’s not blindly auto-filing into patient charts without human oversight. Essentially no change in accountability from the current process (curators were always responsible for data entry accuracy; now they just have an assistant).
Outcome: The clinician agrees that as long as human verification is in place and the evidence is readily accessible, the risk is managed. They might still keep an eye on it, but their opposition is mitigated. We might set up a review committee that includes clinicians to audit the AI’s performance initially, which helps them feel part of the loop (and gives us valuable feedback). In the end, they might find the data quality is even higher than before (because AI doesn’t get tired at 2am and miss something), thus winning their confidence.

I built a product with vision to enable value based healthcare at scale by bridging payers and providers through data and technology. The intent was To create an integrated platform that allows payers and providers to jointly manage patient care outcomes, cost, and quality, thereby aligning incentives and improving health outcomes for members.”

In essence, the product helps configure insurance plans and link them to providers, ensuring that patients (“members”) are correctly attributed to their primary care providers. This enables value-based payment models where providers are held accountable for the cost and quality of care for their attributed patients1. By facilitating accurate patient-to-provider attribution, the platform supports initiatives like Medicare Shared Savings Program (MSSP) and other value-based care contracts where providers who deliver higher-quality, lower-cost care are rewarded1.

Health Plan Creation: Users can create a health insurance plan by specifying Line of Business (LOB) – for example, Medicare, Medicaid, or Commercial insurance – and defining plan details like benefit packages, product IDs, and coverage parameters.
Provider Network Association: After defining a product, users can associate it with healthcare providers that match the plan’s criteria (e.g. providers who serve the same line of business and meet other criteria). This effectively creates payer-provider contracts within the system.
Member Attribution: Once a plan and provider network are set up, the system attributes members (patients) to providers based on rules (e.g. member choice of primary care physician, frequency of visits, or override conditions). This ensures each patient is assigned to the right provider, which is crucial for accountability in value-based care1.
Shared Savings and Cost Management: The product supports a shared savings model, a value-based payment approach where providers are incentivized to reduce healthcare costs for their patient cohort while maintaining quality2. Providers continue to receive fee-for-service payments, but if they keep total costs under a target (benchmark) and hit quality benchmarks, they share in the savings as a bonus2. For example, if a provider’s cost target for a patient is $100 and they manage to spend only $80 by optimizing care, they have achieved a 20% cost reduction; a portion of that $20 saved could be paid back to them as a reward.
Quality of Care Assurance: To prevent cost-cutting at the expense of patient health, the platform integrates quality of care measurements. Providers must meet quality benchmarks (e.g., clinical outcomes, patient satisfaction) in order to fully earn shared savings bonuses2. In our implementation, we incorporated third-party quality ratings (for example, standardized quality scores or star ratings) so that incentives are tied not just to cost, but also to maintaining or improving care quality.
Provider Dashboard for Care Management: The product offers a dashboard for providers that surfaces critical insights about their patient panel. It highlights high-risk patients (e.g., those with chronic conditions or recent admissions), patients who have incurred high costs or undergone high-cost treatments, and patients with care gaps (like missed appointments or lapsed medications). This helps providers prioritize outreach and interventions for patients who need attention, ultimately aiming to improve outcomes and prevent costly health events. By identifying care gaps and at-risk patients, the dashboard supports timely interventions which can improve clinical outcomes and reduce expensive acute care usage3.
Key Components of the product and how they were developed:
Insurance Product Builder: This module enables creation of a health insurance product. As a product manager, I defined the requirements for a flexible plan builder:
Line of Business (LOB) selection: Users choose the insurance type (e.g., Medicare Advantage, Medicaid managed care, Commercial employer-sponsored plan). This selection filters relevant options, since each LOB may have different regulatory requirements and standard benefits.
Product Swim Lane (PSL): This is an internal categorization of the product – essentially a sub-category or segmentation within a line of business. For example, within Commercial insurance, PSL might differentiate an HMO plan vs. a PPO plan as different “swim lanes,” or separate individual market plans from group plans. This concept helped us route approvals and apply business rules specific to that category. (The term “Product Swim Lane” was used to denote parallel product tracks or categories.)
Benefit Package ID tagging: The user can tag a Benefit Package to the product. Benefit packages are collections of benefits (like a predefined set of covered services and co-pay structures). We had a separate module for creating and managing Benefit Packages (each with an ID, and a list of benefits/coverage details). By tagging a benefit package to the product, the plan inherits all those benefit details. This design promotes reusability (common benefit designs used across multiple products) and consistency, especially important for compliance (e.g., ensuring a Medicare Advantage plan includes all CMS-mandated benefits).
Product ID and metadata: Once the plan is configured, the system generates a unique Product ID. Users also enter other components such as plan name, effective year, geographic region, and any specific rider options. The UI guides the user through these inputs, performing validation (for example, if Medicare LOB is selected, it checks that a valid Medicare Benefit Package is attached).
We ensured the plan builder was modular – it can be extended to new lines of business or new benefit rules as needed. During development, one challenge was incorporating varying business rules (like different fields for Medicaid vs Commercial plans) – we solved this with dynamic form behaviors driven by LOB selection.
Provider Network & Contracting Module: After a product is defined, the next step is associating providers to that product. The platform includes a provider directory and contracting interface:
Provider Selection: Users (payer network managers) search and select providers or provider groups to include in the plan’s network. The system filters providers based on criteria such as LOB eligibility (e.g., some providers might only serve Medicare patients, etc.), specialty, location, and even age range of patients they serve if applicable (for instance, pediatricians vs geriatric specialists).
Contract Details: For each provider added, certain contract parameters are set. This includes the applicable LOB, the specific Product or plan, and any constraints like age range of patients (e.g., a pediatric clinic might have age range 0-18 for patient attribution), or service area limitations. Essentially, this defines the scope of patients that can be attributed to that provider under this plan.
Contract Approval Workflow: Once a provider is added to a product’s network, an electronic contract is generated. Providers can review the contract details (e.g., the shared savings terms, quality expectations, and their patient population characteristics) through their interface. They have an ability to approve or sign-off within the system. We implemented a basic workflow for contract approval and if a provider declines or proposes changes, that feedback loops to the payer’s team.
When developing this module, we had to ensure data integrity and compliance – for example, a provider cannot be inadvertently assigned to a Medicare plan if they are not enrolled in Medicare, etc. We integrated NPI (National Provider Identifier) checks and credential status for such validations.
Member Attribution Engine: This is the core logic that runs after a provider network is set up for a product. The attribution engine assigns members to providers using a hierarchy of rules:
Override rule: A manual override has highest priority. For instance, if a member or employer specifically requested a certain primary care provider, or if a provider changed state/licensure and an admin manually reassigns patients, those override attributions are honored first. We built an interface for administrators to make such manual assignments in special cases.
Visit-based attribution: For the remaining members who haven’t chosen a provider, the system uses claims data to find which provider a member visited most frequently in a recent period (e.g., in the last 12 or 18 months). The assumption is that the provider who has seen the patient most often is effectively their main provider. This approach follows industry best practices – many payers attribute patients to the provider who provided the plurality of their care when no formal selection is made1. Our algorithm scans the claims records in the data warehouse and counts visits by provider, attributing the member to the provider with the highest visit count (as long as that provider is indeed in the network).
Member’s PCP choice (self-selection): If the product allows open PCP selection and the member has proactively chosen a primary care physician, that choice is recorded (often via the enrollment process) and takes precedence. (In many insurance plans, members can login to a portal and select or change their PCP. Our system could ingest that data as an override input as well.)
These rules ensure each member is attributed to a single primary provider (or care team) for accountability. Attribution is critical: under value-based programs, payers need to know exactly which patients are assigned to which providers to measure costs and outcomes1. We regularly updated the attribution monthly as new claims came in or as new members joined.
The attribution engine was implemented as a batch process (since it involves heavy data processing on claims). It runs via our ETL pipeline (described below), ensuring up-to-date attribution lists for all providers.
Data Integration and ETL Pipeline: The member and claims data, vital for both attribution and cost/quality analytics, come from external sources:
We built a data pipeline using Informatica (ETL tool) to extract and transform enrollment data (members, their plan enrollments) and claims data (records of healthcare services). These were loaded into a Teradata data warehouse. Each night, incremental loads bring in new claims and membership updates.
We leveraged enterprise job scheduling with Control-M (a workload automation tool) to orchestrate these ETL jobs. Control-M integrates with Informatica workflows, allowing a unified schedule and dependency management for our nightly batch runs4. This meant, for example, the member load runs first, then the claims load, then the attribution engine, in a controlled sequence.
We also used a Workload Manager (WLM) tool in conjunction with Control-M to monitor and optimize resource usage for these jobs. WLM helped ensure that heavy data jobs didn’t overwhelm the database, by prioritizing and throttling tasks as needed (particularly important on the Teradata side, to manage query workloads).
Data Quality and Monitoring: Part of development included setting up data validation checks (e.g., total records counts, basic sanity checks like no null IDs) post-load. If a load failed or data looked inconsistent, Control-M would trigger alerts. Early on, we encountered a few data discrepancies – for instance, a batch of claims with unexpected codes – which caused job failures. We addressed this by adding more robust error handling and alerting, so the data engineering team could quickly rectify issues. Over time, these pipelines became stable, with >99% of nightly loads completing successfully.
4 – Control-M for Informatica allows integration of ETL jobs into a single scheduling environment, which we used to automate and monitor data loads.
Analytics and Dashboard Module: On top of the data, we developed the analytics layer that feeds the provider dashboard and payer reports:
Provider Performance Dashboard: Accessible to providers, it displays metrics like total patients attributed to them, cost of care vs target (showing whether they are on track to save or exceed budgets), and quality metrics (like preventive care measures for their patients, e.g., percentage of diabetic patients with HbA1c under control). It also flags high-risk patients – for example, patients with multiple ER visits or those missing follow-ups. By surfacing these patients, the tool prompts providers to take action (coordinate outreach, schedule appointments, or adjust care plans). Such proactive identification can lead to significantly improved outcomes; industry examples show that intervening on high utilizers can cut costs substantially (one platform reported a 50% reduction in cost for frequent multi-visit patients by active care management3).
Member 360 View: For each attributed member, a provider can view a summary (recent visits, active conditions, medications, and any care gaps). This helps in care coordination. We built this by aggregating claims and, if available, clinical data feeds into one view.
Payer Reports: The payer-side users have access to aggregate reports such as overall cost performance of a plan, utilization trends, and provider scorecards. For instance, a product manager could see how the “Medicare Silver Plan” is performing across the state: total spending vs benchmark, hospital admission rates, and which providers are exceeding or beating cost targets. They also see quality outcomes aggregated (e.g., average quality score by provider). These reports guide adjustments in contracts or additional provider support programs.
We ensured privacy and compliance (HIPAA) in our analytics – providers only see data for their patients, and payer users see de-identified or aggregated data when looking at multiple providers.
Throughout development, we used product management best practices like writing detailed user stories for each feature (e.g., “As a network manager, I want to associate a provider with a product so that members in that product can be attributed to that provider”), maintaining a prioritized backlog, and holding sprint demos with stakeholders to get feedback early and often. This collaborative and iterative approach was critical given the complex domain and multiple stakeholder types (internal teams, payer users, provider users).

Metrics Tracked
From day one, we identified key Key Performance Indicators (KPIs) to gauge the product’s success. These metrics covered both the outcomes the product enabled (e.g., cost savings, care quality) and the usage/engagement of the product (to ensure it was adopted and providing value to users).
1. Patient-Provider Association Accuracy: We measured how effectively the attribution engine was assigning members to the correct provider. Although “correctness” can be subjective, proxies include:
Stability of attribution: e.g., what percentage of members stay with the same provider year over year, which indicates the algorithm isn’t churning assignments needlessly.
Manual changes: how often did we need to use the override feature? If too often, that could indicate the automated rules were missing something. Our goal was to keep manual overrides under, say, 5% of all attributions.
We also tracked anecdotal feedback from providers: if they frequently reported “this patient isn’t mine” or “I have patients not attributed to me that should be,” that would be a red flag. Fortunately, by using plurality of visits as a key criterion, we aligned well with how payers industry-wide define attribution1, and we saw strong alignment with providers’ expectations. In pilot tests, over 90% of attributed lists required no correction, indicating high accuracy.
2. Cost Reduction and Savings: A primary goal was bringing down the overall cost of care for the patient population without compromising quality. We tracked:
Medical cost per member: on a PMPM (per member per month) basis, comparing baseline period to post-implementation. In value-based contracts, a lower trend in PMPM cost is a win. For instance, one year into deployment, a Medicare Advantage plan using our platform might see their PMPM cost drop by a few percentage points relative to the region benchmark, thanks to better care coordination.
Shared Savings Outcomes: We specifically looked at how many provider entities earned savings bonuses and the magnitude of savings. Example: “Number of provider groups under the shared savings model that met cost targets.” If 8 out of 10 groups earned savings, and the total saved amount was, say, $2 million (with $1M paid as bonuses), that’s a measure of success.
A key built-in metric was spending vs target for each contract. We aggregated these to see overall performance. The expectation was that at least some providers would come under target (savings) while others might go over (losses); over time, we wanted the majority to succeed, indicating the program is working. By year 2, one of our early adopting provider groups achieved a ~15% reduction in total cost of care for their patients. In industry terms, such double-digit percentage cost reductions are considered very significant, as shared savings models typically start yielding single-digit improvements initially2.
3. Quality of Care Metrics: Since cost must be balanced with quality, we tracked quality indicators:
We integrated standard healthcare quality measures like HEDIS (Healthcare Effectiveness Data and Information Set) metrics. For example, we monitored what percentage of diabetic patients had their blood sugar tested and controlled, or cancer screening rates, etc., within each provider’s panel.
We also tracked a composite “Quality Score” for each provider (which might come from a third-party rating or our own calculation combining multiple measures). This could be expressed as a percentage or 5-star rating. Our product’s success metric was that providers’ quality scores should remain high (or improve) as their costs went down. Indeed, in our pilot, all providers that achieved cost savings also maintained quality scores above the required threshold. Meeting these quality benchmarks was mandatory for receiving shared savings, reflecting the principle that providers must deliver quality care to get bonuses2.
Patient satisfaction or experience metrics (like CAHPS survey scores) were also considered when available, because a big drop in patient satisfaction could indicate corners being cut. We set targets in line with national averages for these as a floor.
4. Provider Engagement and Adoption: We wanted to ensure that providers actually used the dashboard and took action based on it.
We tracked login frequency and time spent on the provider dashboard. For example, what percentage of providers log in at least once a week? In the early phase, we aimed for at least 75% weekly active usage among our engaged provider group. This was important because if providers don’t use the insights, the impact on cost/quality would be limited.
We also looked at actions taken – e.g., number of high-risk patients flagged vs how many of those got a follow-up appointment scheduled. One feature we added was a simple “Mark as reviewed” or “Schedule follow-up” button next to each flagged patient in the dashboard, so we could get telemetry on whether the platform was prompting real-world actions. High utilization of these actions correlated with better patient outcomes, anecdotally.
On the payer side, user adoption was measured by how many product managers used the tool for plan design (versus old methods). By the second year, all new health plan products were being configured through our system (100% adoption for new products), and legacy products were being migrated. We also measured time taken to configure a product – which went down significantly (what used to take weeks of back-and-forth in spreadsheets now took days to complete and approve through our UI).
5. Operational Metrics: Internally, we tracked the performance and reliability of the system:
ETL job success rate: We wanted nightly data loads to be highly reliable. We monitored the Control-M job success and aimed for 99%+ on-time completion. With improved error handling, we achieved near 100% uptime of the data feed.
System performance: Page load times for the UI, and how quickly the dashboard analytics could appear. We aimed for sub-second load for main dashboards and <30 seconds for heavy reports (given they might crunch a lot of data on demand). We continuously optimized SQL queries, added indexes, and archived old data to keep performance in check.
Release cadence and velocity: How many features or story points we delivered per quarter – to ensure we were executing the roadmap.
These metrics were regularly reviewed in our team’s dashboards. For the interview panel context, I would highlight how we linked these metrics to product decisions. For example, noticing lower login rates for some providers led us to interview them and discover usability issues, which we then fixed in a subsequent release.
Challenges and Conflict Resolution
Developing a complex healthcare product like this came with numerous challenges, both technical and organizational. As a product manager, a key part of my role was managing stakeholder expectations and resolving conflicts when they arose, be it on requirements, design decisions, or timelines.
Stakeholder Conflicts on Features: We had multiple stakeholders – internal executives, the payer users, and provider representatives – each with their own priorities:
One example conflict was between payer needs vs. provider usability. The payer-side stakeholders wanted extremely detailed data captured for each provider contract (to cover every compliance scenario). This made the provider contract UI very lengthy initially. On the other hand, providers testing the system found the onboarding process too cumbersome. I had to mediate and find a compromise. Resolution: We introduced a two-tier approach – a “quick add” for providers with just the essential info to get them onboard, followed by an “advanced details” section that the payer could fill later. This kept providers happy (quick onboarding) while still allowing the payer team to input all needed data eventually.
Another conflict occurred around the attribution algorithm. Some clinical leaders (providers) felt the “visit-based” attribution should consider only primary care visits, not specialist visits, to truly assign the PCP. Meanwhile, the payer analytics team wanted to count all visits (including specialist) as a sign of where the patient is getting care. This was a nuanced debate affecting attribution outcomes. Resolution: I facilitated a meeting where both sides reviewed sample data. We found that including specialist visits sometimes misattributed certain patients. We agreed on a rule to prioritize primary care visits, and only if those were tied, then look at specialist visits. This hybrid rule satisfied both parties. It taught me the importance of evidence-based decisions – by presenting data and potential impact, we resolved what could have been a stalemate.
Throughout such negotiations, I made use of visual aids and data. For instance, I prepared a feature prioritization matrix mapping features to business impact and development effort. This helped when timeline conflicts arose – if a stakeholder wanted a feature that was high effort but low immediate impact, I could visually show why we should deprioritize it for the current release. According to research, using visual representations like roadmaps or priority matrices can increase clarity by 35% during stakeholder discussions5. I found this true in practice – once everyone could see the trade-offs laid out, it was easier to agree on a path forward.
Timeline and Scope Management: Hitting our delivery dates for major phases was critical (especially when tied to annual insurance product launch cycles). However, scope creep was a constant threat:
In one situation, a regulatory change for Medicaid plans was announced mid-development – requiring us to capture an additional data field and logic in the plan builder. Implementing this would risk our timeline for Phase 2. There was pressure from compliance stakeholders to include it immediately. I had to push back and negotiate. Resolution: I communicated a plan to do a minor release (patch) just for that compliance item after the main Phase 2 release. I showed that the development team couldn’t safely squeeze it in without jeopardizing testing of existing features. By committing to a follow-up release (and aligning it with the regulatory effective date), I managed to satisfy compliance needs without derailing the core roadmap. This kind of scope deferral required buy-in from higher-ups, but by showing a clear plan and ensuring minimal risk, I got approval.
Another timeline challenge was with the ETL pipeline readiness. Initially, our data engineering underestimated time to set up the Teradata environment. This put pressure on the later parts (since without data, we couldn’t fully test attribution). Rather than shift the overall deadline, I worked with engineering to re-prioritize feature development – focusing UI work first while data pipeline was being built, then switching to integration and testing once data was flowing. We also added an interim step of using synthetic data to test attribution logic. Through daily stand-ups and tight project tracking, we caught up. It was a stressful period, but it taught the team the value of flexibility and cross-team cooperation.
To keep everyone aligned, I held regular stakeholder check-ins (bi-weekly) where I presented progress and updated the timeline. Being transparent about delays or issues was key to maintaining trust. Moreover, I set up a shared dashboard showing our burndown chart and key milestones. By openly tracking our timeline and scope status, stakeholders felt involved and we reduced panic scenarios.
Design Debates: There were also internal debates, such as:
UI/UX design: Our design team proposed a very modern interface for the provider dashboard, but some internal stakeholders feared it might confuse less tech-savvy doctors. We had conflict on whether to go simple or feature-rich. Resolution: We conducted quick usability tests with a handful of doctor office staff. Their feedback actually supported a cleaner design with clear callouts (they didn’t need flashy charts, just the facts and simple tables). We used this evidence to convince the design team to simplify certain elements. This kind of user-centered resolution helped avoid designing for the wrong target.
Data granularity: The analytics team wanted to expose a lot of data to providers (even cost details for each claim). Our legal team was concerned about sensitive data and potential misinterpretation. We negotiated to aggregate some data (e.g., show total cost by category rather than each claim’s cost) to satisfy both sides – providers get useful info, and legal is assured that raw claims aren’t exposed out of context.
Conflict Resolution Strategies Employed:
One-on-One Discussions: I often held one-on-one meetings with key stakeholders when conflicts arose (instead of only large meetings). This allowed me to truly understand their concerns. In fact, having personal conversations with stakeholders greatly improved alignment and trust; research indicates that engaging stakeholders individually can improve satisfaction and reduce conflict5. By hearing people out individually, I could find common ground or at least acknowledge their perspective when bringing the group together.
Workshops and Feedback Sessions: For bigger conflicts or brainstorming solutions, I ran workshops. For example, we had a half-day workshop with provider reps and payer reps to redesign the provider scorecard in the dashboard to satisfy both. By giving each side a safe forum to voice needs, we reduced misunderstanding by a large margin. Structured feedback sessions like this can cut down miscommunication significantly (studies cite a 42% reduction in misunderstandings when such sessions are used)5.
Data-Driven Decision Making: Whenever possible, I brought data – whether it was user research, performance numbers, or industry benchmarks – to justify decisions. This helped de-personalize debates. Instead of “Stakeholder A vs Stakeholder B”, it became about what the data suggested. For instance, when deciding the priority of adding a new feature for the Commercial line, I showed that 60% of our current users were focused on Medicare Advantage products (hypothetical example), so Medicare-related features should come first. This kind of framing usually won support.
Through these methods, I was able to keep the project moving forward despite the complex interplay of regulatory requirements, user expectations, and technical constraints. In summary, proactive communication, transparency, and collaborative problem-solving were key to resolving conflicts on this project.
Failures and Learnings
No large project is without its setbacks. We certainly had a few failures or missteps, which turned into valuable lessons. I believe discussing these candidly shows adaptability and commitment to continuous improvement.
1. Pilot Adoption Hiccup: In our initial pilot release to a small set of providers, we encountered lower-than-expected adoption of the provider dashboard. Only about half the doctors in the pilot were actually logging in regularly. This was a failure in driving user engagement.
Cause: Through follow-ups, we learned that the training and onboarding for providers had been insufficient. Many providers didn’t fully understand the value of the dashboard or how to use the data. Some were simply too busy and didn’t prioritize an optional tool.
Response: We took this as a lesson and revamped our onboarding strategy. We organized short training webinars and created quick-start guides. We also added in-app tooltips and a tutorial mode for first-time users. Additionally, we identified “physician champions” (doctors who were enthusiastic and successful in the pilot) and had them share testimonials and tips with their peers – making the case that using the dashboard saved them time (for example, one physician champion showed how he used the high-risk patient list to act early and prevent a hospitalization, which impressed others).
Outcome: In the next phase, adoption improved significantly (eventually we achieved ~85% weekly active usage in that provider group). The failure taught me that “build it and they will come” doesn’t always apply – we needed to sell the value and support the users. It underscored the importance of change management in product rollouts, especially in healthcare where users already have many systems to deal with.
2. Attribution Algorithm Flaw: After going live, we discovered a scenario where the attribution logic was failing – specifically, when a provider left the network or a clinic closed, some members were left unassigned or still attributed to the now-departed provider. We hadn’t built a re-attribution on provider exit; this was an oversight.
Incident: In one case, a provider moved out of state and our system didn’t immediately reassign those members to new providers. As a result, those members weren’t appearing in any provider’s dashboard, which meant they could fall through the cracks in care management.
Resolution: Once identified, we treated it with urgency. The engineering team quickly implemented an “attribution refresh” routine that would automatically re-run attribution for any members whose provider had left or been removed, essentially catching the orphaned patients and reassigning them per the visit logic. We also updated the interface to flag if a provider is being removed from a network: the user must choose how to redistribute their patients (either assign to a specific new doctor or let the system auto-distribute them).
Learning: The lesson here was to consider edge cases and fail-safe mechanisms. We instituted more rigorous testing for scenarios like provider termination, adding test cases to ensure members are never left unattached. It also highlighted the value of monitoring – we added a metric for “unattributed members” and set up an alert if that ever goes above zero in a given plan. This failure, fortunately, was caught early with minimal patient impact, but it could have been worse if unnoticed.
3. Performance and Scaling Issue: As the data volume grew (especially after adding multiple lines of business and more providers), we hit a performance bottleneck. One of our batch attribution jobs started taking too long and spilling into working hours, affecting system responsiveness.
Cause: The logic was initially written in a way that was not fully optimized for the large data set (for example, it was scanning the entire claims table for each run). With more data, it became slow. We also had not partitioned the Teradata tables optimally at first.
Addressing the Failure: We treated this as a chance to improve the system’s robustness. Database experts were brought in to help optimize the query and index strategy. We partitioned data by year and line of business which drastically improved query performance. We also refactored the code to do incremental attribution (only for new or changed data, rather than recalculating everyone each time). Additionally, we adjusted the schedule so that even if an ETL job ran long, it wouldn’t block the user interface (decoupling some of the processes).
Outcome: After these fixes, the performance issue was resolved and we had headroom for future growth. The key learning was scalability planning – building for scale from the beginning. In retrospect, we could have simulated larger volumes early on. Nonetheless, the team gained valuable experience in performance tuning. It also reinforced the importance of having a staging environment with production-sized data for testing as we go (something we invested in after this incident).
4. Stakeholder Communication Miss: At one point, we almost had a failure in stakeholder management – not a product failure per se, but an important lesson. We had decided internally to remove a minor feature (an “export to Excel” function for one of the reports) due to time constraints. We assumed it was not critical. However, we failed to inform one key stakeholder from the payer operations team who really wanted that feature.
When the release went out without the export function, that stakeholder was unpleasantly surprised and escalated the issue. It created some friction and made it look like we disregarded input.
Resolution & Lesson: I took responsibility for the oversight, apologized, and scheduled a quick patch in the next sprint to add the export function (which we did deliver soon after). More importantly, I learned never to assume a feature is “minor” to a user without confirming. We improved our change communication process – any time we consider de-scoping something that had been promised, we now explicitly discuss it with stakeholders and update the specification documents. Transparency and setting the right expectations are crucial; this incident reminded us to keep stakeholders closely in the loop to maintain trust.
5. Post-Mortem Culture: After each major release (and especially after any failure/issue), I conduct a post-mortem review with the team. For instance, after the attribution bug and the performance issue, we held sessions to document what went wrong and why. We used a blameless approach, focusing on process improvements. These reviews directly led to actions: e.g., adding the unattributed members monitor, investing in performance tests, improving communication as mentioned. By iterating on our processes, we reduced recurrence of similar issues. A big takeaway is that continuous improvement is part of the product management process – learning from failures ensures the product and team become more resilient.
In conclusion, working on this healthcare payer product was a challenging but rewarding experience. From a product manager’s perspective, it required deep domain knowledge (health insurance operations, value-based care models) and strong cross-functional leadership to bring the vision to life. The product achieved its core mission of enabling payer-provider collaboration to improve patient outcomes and cost of care. Moreover, the journey taught me invaluable lessons in stakeholder management, agile development, and the importance of balancing innovation with reliability in a high-stakes domain like healthcare.
